# 架构：为什么这样分层

## 问题

一台机器要跑代理，通常需要三样东西：

1. 节点 —— 机场提供，会变，会过期，名字会改。
2. 规则与策略组 —— 你自己整理，希望稳定，希望多机一致。
3. 当前选择 —— 只有这台机器关心，且随时会被改。

传统做法是把三样塞进同一个配置文件，用一个脚本或面板管理。结果是谁改都会互相踩：

- 机场更新订阅，把你手写的规则覆盖掉。
- 你在面板上切了节点，脚本重新生成配置，选择回到默认。
- 你想在第二台机器上复用规则，只能复制整个配置文件，连节点凭据一起复制。

## 分层

```
merge-base.yaml         运行时骨架：DNS / sniffer / TUN / CORS / mode ……   本机
      +
shared-rules.yaml       rules / rule-providers / proxy-groups              仓库
      =
Merge「自管规则与地区策略」                                                  本机容器
      +
基础配置                 proxy-providers.active → 机场订阅                 本机容器
      =
运行配置                                                                     内核
```

关键决定：**Merge 只允许包含三个键**（`rules`、`rule-providers`、`proxy-groups`）。这是 MetaCubeXD 的 Merge 机制本身能做的事，也是分工的自然边界。

- 只有这三个键可共享，因为它们与节点和本机环境无关。
- 运行时设置（DNS、TUN、CORS）留在本机的 `merge-base.yaml`，不进仓库：它们与机器的网卡、端口、面板地址绑定。
- 机场凭据只出现在基础配置里，不进仓库、不进 Merge。

## 节点由内核自己拉

基础配置里唯一与机场有关的东西是一个 `proxy-providers.active`：

```yaml
proxy-providers:
  active:
    type: http
    url: https://机场订阅链接
    path: ./airport.yaml
    interval: 21600
    proxy: DIRECT
```

分工落在这里：

- **内核负责拉。** 按 `interval` 自己生成请求、自己写 `path`、自己按 `health-check` 测速。没有外部下载脚本，定时器 `sync` 也不碰它。面板只在 `/providers/proxies` 里显示状态。
- **只取 `proxies`。** 订阅里的 `rules`、`proxy-groups`、`dns` 全部丢弃。这就是「机场只提供节点」的实现方式，也是为什么不存在「机场规则混进自管规则」这种可能。
- **组靠引用，不靠复制。** 策略组写 `use: [active]`，节点名换了一轮，组的成员自动跟着换。所以仓库里的 `proxy-groups` 不需要知道任何具体节点名——这是它能跨机器共享的前提。
- **凭据只在本机。** `url` 里带令牌，所以它只在基础配置里出现；仓库里那份 `shared-rules.yaml` 只引用 provider 的名字 `active`，不含 URL。

这带来一个必须遵守的约束：**仓库定义的组筛选方式，要能匹配所有机器上 provider 给的节点名。** 某台机器自己留着旧组定义、只更新 provider，面板看起来正常，实际筛选已经和仓库对不上。这也是「本地差异」在这套架构里没有位置的原因。

`check_shared()` 用白名单而不是黑名单：出现第四个键就拒掉，不猜用户意图。

## 期望状态，不是增量补丁

`sync` 不做「读现有配置 → 改一处 → 写回」。它从零构造期望状态：

```
期望 Merge = merge-base.yaml | shared-rules.yaml
```

然后把运行配置收敛到它。这样有几个直接好处：

- **幂等。** 已经一致时什么都不写。手改过 Merge 也会被拉回来。
- **可审计。** 仓库里的文件就是唯一真相，不存在「机器上的配置是什么」这个问题。
- **可回滚。** 不需要记「上次改了什么」，只需要一份完整快照。

代价是每次同步都要重算全部三个键。对 6000 条规则、35 个组这个量级，成本是毫秒级，可以接受。

## 顺序：先校验，后写入

任何写操作前面都有一道 `mihomo -t`。校验失败就什么都不写。

校验用哪个二进制，取决于容器有没有起：

- 容器在跑 → `docker exec` 在容器里校验，环境与运行时一致。
- 容器没起（装机阶段）→ 用 `data/mihomo` 在宿主就地 `-d data` 校验，因此 geo 数据必须与二进制一起拷到位。

这条规则的来源是实践：先写后验等于把坏配置推进内核，内核起来才发现问题，此时已经断网。

## 先取 SHA，再取文件

GitHub 的 raw 内容是「最新版本」，不是「某个版本」。如果先读文件的元信息再读内容，中间有人推了新 commit，就会读到新旧混杂的两个来源。

正确做法是：先取 `commits/main` 的 SHA，再按 `?ref=<sha>` 读文件。任何时刻读到的都是同一个 commit 的一致快照。

`github_get()` 还会在代理与直连之间交替重试（最多 5 次）：api.github.com 直连在某些网络下会偶发 TLS 阻断，代理走 HTTP/1.1 更稳。

## 选择存在内核里

「当前用哪个节点」不是配置文件的一部分，它是内核的运行时状态（每个策略组一个 `now`）。

因此同步前后各做一次：

- 写之前 `snapshot()` 收集所有带 `now` 且有 `all` 的组 —— 不按组类型筛选，因为地区组是 `url-test` 但同样有 `now`，只记 `select` 会漏掉 7 条。
- 写之后 `restore()` 只有当目标节点仍在候选清单里才切回去。机场换了、节点改名了，这一条就静默跳过而不是报错。

## 失败必须可回滚

同步的写操作分三步：写 Merge → 重新激活 → 回读确认。中间任一步失败，运行配置可能停在半套状态。

所以写之前先把当前 Merge 存成 `merge-before-last-sync.yaml`，异常路径统一走 `_rollback()`：把快照写回、重新激活、再做一次不花流量的验收。

这里有一个刻意的取舍：回滚是尽力而为。如果内核本身已经起不来，回滚也会失败，错误会连带抛出去。真正的兜底是「写之前校验」和「写之前快照」，而不是「写之后能救回来」。

## 验收看行为，不看返回码

`200 OK` 只能说明接口收到了请求。`verify()` 检查的是内核实际加载了什么：

- `/proxies` 里地区组类型是 `URLTest`、成员是本机 provider 节点的子集。
- `/rules` 条数与期望相等。
- `/providers/rules` 名字集合与期望相等。
- DNS 同时应答 TCP 与 UDP 查询。
- 经代理口访问三个固定返回码的端点。

出口探测只挑稳定端点：google 系根路径会随节点出口给 404 或 000，不具备诊断价值，换成 gstatic 的 `generate_204`。

## 不做的事

- **不跟 `latest` 镜像。** digest 写死在脚本里，升级是显式动作。
- **不在面板里点「同步」。** 同步只有 systemd 定时器和手动 `sync` 两个入口。
- **不解析机场的规则。** 订阅里的 `rules`、`proxy-groups` 全部弃用，只取 `proxies`（通过 `proxy-providers` 自动注入）。
- **不做多机编排。** 每台机器一份 `merge-base.yaml`、一个 `deployment.json`。共享的是仓库里的文件，不是部署状态。

## 与 Sub-Store 的关系

Sub-Store 是另一条路：它把节点和规则一起加工成一个完整配置文件，交给客户端。

两者的差别在于**谁持有最终配置的组装权**：

- Sub-Store 的方案里，转换器输出完整配置，规则是输出的产物。
- 本方案里，规则是输入（仓库），组装在每台机器上做，产物是运行时状态。

当规则需要版本管理、需要多机一致、需要能回滚的时候，前者的问题是规则藏在转换脚本里，不在版本控制里。这是本方案存在的原因。
